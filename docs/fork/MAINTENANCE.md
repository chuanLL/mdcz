# Fork 维护流程

本 Fork 用于持续维护自己的 MDCz 改动，同时接收官方更新。保留上游项目的许可证、署名和提交历史。

## 仓库与分支

| 名称 | 作用 |
| --- | --- |
| `origin` | [chuanLL/mdcz](https://github.com/chuanLL/mdcz)，自己的 Fork |
| `upstream` | [ShotHeadman/mdcz](https://github.com/ShotHeadman/mdcz)，官方项目 |
| `main` | 跟踪官方主分支，保持干净；只做可快进同步 |
| `nas-maintained` | 自己的维护版本，包含已验证补丁与本页维护约定 |
| `fix/*`、`feat/*` | 独立改动；适合通用修复时向官方提 PR |
| `sync/upstream-*` | 在隔离分支验证上游合并，验证后推进维护分支 |

初始官方基线：0.22.0，提交 `e869dc74e44d7e21d5ad5ed33ad9e40e5abed9be`。翻译拒绝回退修复提交为 `31c9c3e33ed993f72172ff85249b0b7952cdd34e`；向官方提交的 [PR #167](https://github.com/ShotHeadman/mdcz/pull/167) 与维护分支分开，避免把 Fork 专用约定混入通用修复。

这些是历史基线，当前版本和 PR 状态须实时核对。

## 日常迭代与同步

当前采用用户按需发起的手动检查，不设定时任务。需要检查更新或同步官方代码时执行下面的流程。

1. 开始前读取根 `AGENTS.md`、本页和相关模块规则；核对远端、当前分支和未提交改动。
2. 新需求从 `nas-maintained` 建独立分支，只提交代码、必要测试和公开文档。测试遵守根规则，使用中性合成输入；不读取真实媒体或调用生产模型作为常规测试。
3. 检查上游时获取官方 `main`、最新正式 Release 和相关 PR 的实时状态。同步前判断官方是否已经以相同或不同实现修复本地问题，避免重复叠加补丁。
4. 若有新提交，从最新维护分支建立隔离工作树与 `sync/upstream-*` 分支，在其中合并 `upstream/main`，检查冲突、依赖、配置、数据库迁移和 Docker 入口的变化。
5. 根据差异运行相关测试、类型检查、格式检查和必要构建。发布过的迁移不改写；出现冲突、检查失败或需要新架构决策时保留可审阅结果，先解决问题，不强推、不自动覆盖工作区。
6. 检查通过后可把验证后的同步提交推进到自己的 `nas-maintained`。`main` 只接受官方历史的快进更新；若已产生本地分叉，先调查原因。每次推进前重新核对远端分支，防止覆盖其他人的提交。
7. 通用改进使用独立分支向官方贡献；不因自己的维护分支可用而声称官方已经采纳或发布。

## 部署与回退

代码合并不等于生产更新。NAS 运维记录、配置、密钥、数据库、媒体、备份及设备地址保存在私有运维工作区，本公开仓库不保存这些内容。

生产部署单独授权与验收：先核对实际运行版本、挂载、数据库和配置备份，以及是否存在同版本运行补丁的 bind。变更官方镜像前判断旧 overlay 是否应移除或重新构建；不能把旧版本 server.js 无条件挂到新镜像上。需要数据库迁移时准备对应数据回退方案，单独回退镜像未必足够。

记录清楚代码已合并、本地验证通过、镜像已构建、设备已部署及同层验收的不同状态。本文不把任何历史运行结果当作当前设备证据。
